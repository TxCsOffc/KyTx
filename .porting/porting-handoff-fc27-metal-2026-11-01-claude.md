## Что изменено в коде сегодня (всё незакоммичено)
1. **`KYTY_MSL_WAVE64` теперь включён по умолчанию** (`MslEmitter.cpp` `Wave64Pair`: `getenv == nullptr || [0] != '0'`; `KYTY_MSL_WAVE64=0` выключает). Основание: ~25 запусков 2026-10-27…11-01 с включённым wave64 (150–420 с) не падали; без него — шум/полосы. Прежняя запись «25% падений при загрузке» не воспроизводится.
2. UMA (`KYTY_UMA_SURFACES=1`, по-прежнему opt-in): таблица записи GPU — точный стартовый адрес (`GpuWriteStamp`, возраст ≤4 флипа; `KYTY_UMA_RANGE=overlap` — склеенные диапазоны, для сравнения); графический сэмплинг через ту же таблицу (`GraphicsImageFor`); гостевой pitch (`GuestViewRowBytes`) для RT-видов и `GpuSurfaceFor` (`KYTY_UMA_PITCH=tight` — прежнее правило); диагностика `KYTY_LOG_UMA=1` (`[UmaGfx]`), `KYTY_LOG_UMA_BUF=1` (`[UmaBuf]`, много ложных срабатываний: кэшированные виды перекрывают мелкие буферы).
3. Диагностика: GPU-watchdog печатает операции зависшего командного буфера (`KYTY_MTL_GPU_TIME=1`); состояние draw'а в PassTrace дополнено `cbm= rop= shm=` (режим CB, ROP3, маска шейдера); `KYTY_LOG_CP_WRITES=<lo>,<hi>[,<min>]` + `KYTY_TRACE_CP_WRITES=1` (`cpWriteTrace.h`) печатает записи command processor в диапазоне (за ~4000 флипов не нашло ни одной CP-заливки ≥4 КБ нигде, ни одной ≥64 КБ в пуле RT).
4. Скрипты `.porting/work/`: `img_run.sh <tag> <uma 0|1> [сек] [первый флип]` (кадры + все промежуточные картинки; `EXTRA="K=V ..."`, `RANGE=overlap`), `trace_run.sh <tag> <сек> <флип> [шаг]` (pass-trace; `UMA=1`; `EXTRA=` — например `KYTY_PASS_TRACE_FLIPS=3` — **окно трейса по умолчанию ровно один flip, это часть игрового кадра**, нужно 3), `dumpsheet.py`, `tracescan.py <лог> <строка-начала> <строка-конца>` (сводка проходов трейса, помечает первый «насыщенный»).
5. **Ловушка запуска:** `run1.sh` отказывается стартовать, если в `ps aux` есть строка, совпадающая с `kyty_emulator.* --game`, — включая командную строку моей собственной Bash-команды/зависшей фоновой задачи, где в тексте есть и `kyty_emulator`, и `--game`. Тогда `img_run.sh` ждёт вечно «done». Не склеивать сборку и запуск в одну команду; при зависшей задаче — `TaskStop`.

## Найденное (что НЕ является причиной / что причина)
- **Не причина:** ROP3 (все draw'ы `rop=cc`), режим CB (все `cbm=1`), CP-заливки RT-памяти (нет), зависание (закрыто).
- **Освещённая HDR-цель стартует «грязной»:** три аддитивных draw'а света (`vs c7354219 …`, blend 1/1, stencil, indirect `[3,N,0,0]`) пишут в цель `RG11B10 1600x904`, которой до них никто в кадре не касался; уже после draw'а с 0 экземпляров её макс = 65024. В трассе нет ни одного прохода/буфера/заливки, который бы её инициализировал. Реальный GPU обязан где-то её очищать; **механизм очистки не найден** (ищем: проход вне окна трейса? иная инициализация? метаданные?). Рабочее объяснение: игра очищает/инициализирует цель способом, который наш Metal-путь не исполняет.
- **Входы прохода освещения берутся из чужих объектов:** PS `498916464e6bfac3` (2461 строк MSL, аддитивный полноэкранный проход; выдаёт на всём экране константу 64512 — клэмп шейдера): slot67 `0x8245620000` RG11B10 1600x904 → последний писатель по реестру — R16F-картинка прошлого флипа, 675 тыс. NaN; slot69 `0x82447e0000` → писатель 1024x512 R32F; т.е. реальные продюсеры в текущем кадре не найдены, читаются «чужие» текстуры/устаревшая гостевая память (aliasing + реестры «последний писатель»).
- Первое тайловое ядро освещения (`cs 9cc3a5135b60beba`, ~48 вариантов-ядер по типам тайлов; сумма групп за кадр ≈26–36 тыс. ≈ экран 22.6 тыс. 8×8-тайлов, то есть списки тайлов вероятно верны) пишет RG11B10-цель с NaN (848 тыс. каналов) — оценка NaN идёт по всей текстуре, включая ещё не записанные тайлы; клэмп в конце ядра `fmin(buffer[0][0x1f]=64512, x)` (NaN → 64512), поэтому «белое» = 64512. Нулевые входы: BRDF-LUT `0x81b6f70000 128x128 f115` (все нули), 800x452 f10/f92 (в одном запуске нули, в другом нет).
- Трассировщик первого NaN для compute (`KYTY_MSL_NAN_TRACE=<хэш>`) печатает `groups=1x1x1: no NaN float result` для indirect-dispatch'ей (диспатч помечается группами-заглушками) — для таких ядер не информативен; требует доработки (хранить реальные группы).
- UMA-линейные виды vs тайловые raw-буферы: гипотеза о несовместимости не доказана (лог `[UmaBuf]` слишком шумный).

## Что делать дальше (по приоритету)
1. **Найти, как игра инициализирует HDR/аккумуляторные цели.** Идея: трассировать окно 4 флипа (`KYTY_PASS_TRACE_FLIPS=4`) и искать любые операции над адресом цели *до* первого draw'а освещения (в т.ч. RT-проходы с другим форматом на том же адресе, пропущенные «metadata»-проходы, DMA, `COPY_DATA`), либо сравнить число draw'ов с `[DrawAuto] skip` и dropped. Не терять: `KYTY_CLEAR_HDR_FIRST` показал ожидаемый эффект.
2. **Решить архитектурный вопрос поверхностей:** (а) довести UMA (нужно разобраться с тайловыми raw-буферами), либо (б) портировать идеи Vulkan `TextureCache::ResolveOverlap/InvalidateMemory` в Metal-реестры (идентичность поверхности = адрес + выровненный pitch/высота, а не размер дескриптора; чтение чужого формата — через гостевую память с конвертацией), либо (в) гибрид: UMA только для графических RT и их сэмплинга, compute-образы остаются отдельными текстурами с явными конвертациями.
3. Прочее по меню: экспозиция/bloom, белые материалы, чёрные кадры; затем матч, затем FPS ≥30.

## Дополнение 2026-11-01 (Opus, после лимита): ядро классификации тайлов и GDS
**Факт.** Ядро классификации тайлов (гостевой `0xc29caf0c1cb0ad94`, 144 группы × 16x16, persistent threads: поток 0 группы берёт номер работы `ds_inc` по адресу 4, сравнивает с числом работ по адресу 0) в Metal с wave64 **ничего не писало** (r1 f115 и r2 f55 — нули), у эталона r1 есть данные. Лимит циклов не причина (`KYTY_LOOP_CAP=1048576`, um26). Новый переключатель `KYTY_MSL_WAVE64_SKIP=<хэш>[,<хэш>...]` (`MslEmitter.cpp` `Wave64Pair`, гостевой хэш) — ядро без пары wave64: um27 → ядро пишет (r1 ±65504, NaN как у эталона).
**Причина-кандидат (общая).** В MSL ядра число работ читается из `kyty_lds[0]`, в который **никто в ядре не пишет** (неинициализированная threadgroup-память: от неё зависит, будет ли работа вообще; с wave64 там оказывался 0). SPIR-V путь (эталон) направляет все DS-операции с битом GDS (чтения/записи/атомики) в GDS-буфер (`PrepareMemoryResourceAccess` → `gds_variable`), а MSL-эмиттер направлял в GDS только `ds_append/ds_consume`, всё остальное — в LDS. **Исправлено:** при `KYTY_MSL_GDS=1` (все скрипты его ставят) чтения/записи/атомики GDS в compute идут в `ab.gds` (`GdsMem()`, `kMslGdsDwords=16384`, адрес без базы M0 — как в SPIR-V). Тесты `tools/test_metal_msl.sh` проходят. Проверка — прогон um28 (wave64 везде, `KYTY_MSL_DUMP_DIR=artifacts/2026-10-27/um28/msl`, `KYTY_LOG_GDS=1`).

**Исправление 4 (уточнено): предохранитель циклов — счётчик на каждый вход в цикл.** Общий счётчик 65536 на вызов (um40/um41) вызвал зависание GPU (`kIOGPUCommandBufferCallbackErrorHang`, дальше все буферы «InnocentVictim», картинка замирает): огромные forward-PS `0x4a09ccd7…` (52 тыс. строк, 20 циклов) и `0x8e4838bd…` (56 тыс. строк) в HDR `0x8245620000` — перебор источников света по битам маски тайла (≤32), тело ~17 тыс. строк, внутри циклы с границами из SRT (`flattened_srt[0xe9|0xed|0x10e]`). Ошибка командного буфера теперь печатает его операции (`[Metal] ops of the failed command buffer`, нужен `KYTY_MTL_GPU_TIME=1`).

## Дополнение 2026-11-01 (Opus, продолжение): пиксельный зонд, bloom, память
**Инструменты (трасса).** `KYTY_PASS_TRACE_PIXEL=u,v[/u,v...]` (доли размера; `/` — разделитель, `;` ломает `export` в env-файле) — у каждого изображения в трассе печатается `px(x,y)=…` в этой точке: экранную точку можно проследить через G-buffer → освещение → HDR → bloom → тонмаппинг. Трасса теперь показывает привязанный **уровень mip** (вид T# base..last), а не уровень 0 всей текстуры (`PassTraceRebind`). `INPUT=` в `trace_run.sh`/`img_run.sh` — свой автоввод (`...,3300:j:8` доводит до 3D-сцены ожидания; иначе часто остаётся экран FC News).
**Найдено и исправлено:**
1. **Утечка alias-текстур** (`AliasedImageFor`): ключ включает размер, а динамическое разрешение меняет размер каждые несколько кадров → тысячи полноэкранных mip-текстур, >20 ГБ за 90 с (`run1.sh` останавливал прогон). Теперь записи, не запрошенные 120 кадров, удаляются. Цепочка уменьшения просит уровни по одному (2, 3, … 11) — текстура пересоздавалась на каждый диспатч и теряла записанные уровни; теперь новая текстура сразу получает наибольшее число уровней, когда-либо запрошенное для (адрес, формат) (`s_level_hint`). Не делать: «полная цепочка сразу» (um51 — графические шейдеры видят незаполненные уровни) и копирование уровней блитом внутри `AliasedImageFor` (um52–um55 — шум: образы привязываются, когда compute-энкодер диспатча уже открыт, `EndCurrentEncoder` ломал диспатч).
2. **Формат compute-образа**: при совпадении размера текселя (RG11B10↔R32Uint и т.п.) привязывается вид объявленного формата, а не объект чужого формата.
3. **Графическая выборка без подходящего объекта на адресе, который GPU писал в последние 2 кадра, когда у писателя другой размер текселя** → пустой образ (`AliasedImageFor`), как у эталона; раньше декодировались гостевые байты чужого ресурса. (Без условия о размере текселя хуже: RT — виды гостевой памяти, и читатель того же размера текселя, например 1616x912 над 1600x904, декодирует верные данные.) Пример: draw DoF-оверлея (PS гость `ac6862e0`, Metal `0x125da093…`, тинт × выборка 800x452 RGBA16F) читал R8-маску CoC как RGBA16F → NaN/31232 в HDR-сцене → bloom разносил это по кадру (пурпурная дымка, белые пятна). `KYTY_GFX_GUEST_DECODE=1` — старое поведение.
4. `KYTY_SNAPSHOT_STAGING=1` (opt-in, не проверено): все read-only compute-буферы в CPU-арене `0x8190…–0x81a0…` до 512 КБ копируются при кодировании. Старый переключатель `KYTY_SNAPSHOT_SKIN_UPLOAD` был привязан к Metal-ключу ядра копирования матриц костей (`0x0cf7218b…`), который давно сменился — он не срабатывал. Гипотеза: «шипы» от игроков = матрицы костей из кольца загрузки CPU, перезаписанного до выполнения копирования (см. handoff 2026-10-25 вечер).
**Ещё не решено:** длинные тёмные треугольники-«шипы» от игроков (скиннинг), растянутые объекты (скамья/щит на весь экран), бирюзовая промо-картинка FC News на весь экран, кадр то нормальный, то белый/чёрный. Экземпляр `KyTxMetalS1.app` однажды запустился сам/вручную сразу после конца прогона (RUN_TAG прошлого прогона) — проверять `pgrep` перед запуском.
**Результат um56 (`artifacts/2026-11-01/um56/`, конфигурация пользователя):** лучший за день — The Grounds с небом и облаками, FC News поверх 3D-сцены (как у эталона), улицы с фонарями, ~30 FPS, память ~12 ГБ. Остаётся: игрок растянут/размазан и тёмные клинья-«шипы» (скиннинг/вершины), земля то белая, то чёрная, отдельные кадры — сплошной шум. A/B-переключатели: `KYTY_CS_NO_FMT_VIEW=1`, `KYTY_GFX_GUEST_DECODE=1`, `KYTY_SNAPSHOT_STAGING=1` (проверка — um57).
**A/B um57 (`KYTY_SNAPSHOT_STAGING=1`):** хуже (шум, пересвет), «шипы» от игрока остались → гипотеза о гонке с кольцом загрузки CPU не подтвердилась; переключатель оставлен выключенным. **um58 (повтор конфигурации um56):** другая сцена (улица/интерьер) и сильные горизонтальные полосы — растянутые объекты через весь экран (то же, что «скамья» в um45: в G-buffer нормалей объект уже растянут, т.е. ошибка вершин/геометрии, до освещения). Разброс между прогонами очень большой — сравнивать изменения только по нескольким прогонам/сценам.
**Следующий шаг (приоритет):** растянутая геометрия и «шипы» — найти draw: пиксельный зонд (`KYTY_PASS_TRACE_PIXEL`) в точке растянутого объекта на G-buffer нормалей (`RT0 … f90/f70 1600x904`) покажет draw, который меняет этот пиксель; затем его VS (формат вершин, матрицы из пула `0x817d…`).
**Исправление 5 (главное по геометрии): вид гостевой памяти для буферов draw'ов — на весь диапазон V#** (`metalRenderer.mm`, привязка буферов стадии). Обёртка гостевой памяти запрашивалась размером `max_byte_extent` (статически: смещение + ширина доступа; для доступа по динамическому индексу — десятки байт → одна страница), и `sizes[b]` обрезался до неё: всё за первой страницей читалось нулями. Пул матриц костей игроков (`0x817d…`, 25 МБ, индекс из вершины) давал нулевые матрицы → вершины с w = 0 → «шипы»/клинья от игроков и растянутые объекты через весь экран; случайность между прогонами — была ли в кэше страниц обёртка побольше. Теперь размер вида = max(max_byte_extent, V# до 256 МБ); если диапазон не отображён — откат к одной странице. Compute-путь уже брал размер из V#. um60: улицы с игроком без «шипов», красный интерьер без клиньев. Осталось: пурпурно-белые засветки (bloom) в части кадров The Grounds.

## Дополнение 2026-11-02 (Opus): трасса по детектору, насыщение HDR, устаревшие копии гостевых текстур
**Инструменты.** `.porting/work/mt_trace.sh <tag> [сек] [макс. трасс]` — прогон как `mt_shots.sh`, окно снимается каждые 6 с; когда доля почти белых пикселей > `THR` (по умолчанию 0.45), скрипт сам трогает триггеры PassTrace и дампа кадра (`watch.txt` в папке прогона: время, флип, доля белого, TRIGGER). `PIX=u,v/...` — пиксельные зонды, `EXTRA=` — прочие переменные. `KYTY_PASS_TRACE_SAT=<v>` (новое) — у float-изображений трассы: число текселей с каналом ≥ v, их рамка, сетка 4x4 количеств и первый такой тексель. Скрипт разбора `scratchpad/probepath.py` (путь зондов по проходам) — см. ниже, не в репозитории.
**Факты (um64/um65, FC News поверх The Grounds):**
- Бирюзовое свечение = цепочка bloom: вход 1600x904 RG11B10 содержит ~5000 текселей 65024 (насыщение), уровень 1x1 даёт среднее (3.4, 64, 61) — бирюзовый ореол.
- Источник насыщения — цель `0x8245620000` (RT3 MRT G-buffer, потом RT0 аддитивных draw'ов освещения `99ae8630`/`0ef96a06`/`dec48a13` со stencil ref=4, потом вход r8 compute-освещения `0e838ae6…`). На первом draw'е окна трассы в ней уже 5052 насыщенных текселя в **верхних 91 строке** (небо, x 800–1200), draw'ы G-buffer их не трогают. **Окно трассы начинается посреди прохода G-buffer** (перед `begin frame` в логе уже идут DrawIndex в `rt0=0x8240180000`), поэтому очистку в начале кадра одним флипом не увидеть — нужен `KYTY_PASS_TRACE_FLIPS=2` (um66/um67 сцену с 3D не поймали: FC News с промо/шумом).
- Пропусков draw'ов нет (`[Draw] ok ... skipped=0`, только 4 metadata-прохода CB_COLOR_CONTROL.MODE=2).
- Сравнение с эталоном `vk2/shot-180.png` (тот же экран FC News над The Grounds): у эталона голубое небо с облаками, зелёные деревья, игрок в белой форме, полосатая стена; у Metal небо пересвечено, деревья белые, стена — рыжие блоки, игрока нет, логотип FC27 слева вверху — цветной шум, трибуны каждый кадр другого цвета (зелёные/красные/пурпурные блоки). С `KYTY_CLEAR_HDR_FIRST=1` небо чёрное → небо в нашей картинке — старое содержимое HDR-цели, проход неба фактически не пишет.
**Найдено: копии гостевых текстур никогда не обновлялись.** `GuestTexture` (`s_guest_textures`) возвращал закэшированную копию по адресу, если совпадает раскладка и в копии были ненулевые байты, — навсегда. Защиты страниц от записи в нативном Metal-пути нет (`pageManager.cpp` `Protect`: «Apple Silicon UMA… elide»), у Vulkan-пути она есть (поэтому у эталона логотип верный). Любая текстура, которую CPU потом записывает в ту же память (стриминг в переиспользуемые блоки пула, промо-картинки FC News, значок профиля), оставалась старой копией (часто мусором, лежавшим там раньше). **Исправление:** при создании копии (детайл, mip-цепочка, BC, линейная копия) запоминается хэш исходных байт (`GuestTexSourceHash`: целиком до 64 КБ, иначе 4 окна по 512 байт), раз в флип при привязке хэш сверяется, при изменении копия декодируется заново (`[TexRefresh]` в логе, первые 32). Линейный вид на гостевую память не проверяется (он и так живой). `KYTY_GUEST_TEX_NO_REFRESH=1` — старое поведение.
- Проверка um68/um73: перезагрузок мало (1–2 копии на ~1000 флипов, `[TexRefresh] flip=N: K copies ... since flip M` каждые 300 флипов), FPS ~30 не изменился. Compute-путь (`ComputeGuestImageFor`, read-only образы) сверяет хэш **на каждом диспатче** (`s_guest_tex_check_each`), графика — раз в флип.
**Логотип FC27 (левый верх FC News) — не решено.** Рисует draw PS `0x40bdc5e4…` (гость `2ae1ba74`) из BC3 156x72 (tfmt 173, tile 9). Последний GPU-писатель адреса — образ 39x18 RGBA32Uint (16-байтные BC-блоки) ядра копирования текстур `0xa3465640e918640b` (гость `e5941d54`, 8x8, читает `image_0` uint4 и пишет `image_1` со сдвигами из SRT 0x12–0x15; за прогон создаёт ~800 alias-образов RGBA32Uint — `[AliasImg] ... cs=` теперь печатает хэш ядра). `AliasConvert` доверяет писателю только 2 флипа, логотип читается через ~500 флипов → декод гостевой памяти: **блочные силуэты букв, залитые шумом** (данные в памяти почти верные — подозрение на декод BC3 tile 9 или формат). Опыт `KYTY_ALIAS_OLD_WRITER=1` (доверять старому compute-писателю, пока хэш гостевых байт не изменился; хэш берётся в `RecordComputeStorage(..., hash_guest=true)`): логотип чёрный — источник копии (64x64 RGBA32Uint, tile 9, `0x81b4fc0000` в начале загрузки) был нулевым в момент кодирования (`[Detile] ... nz=0`, `GUESTMISS registries: none`), т.е. его заполняет что-то, чего Metal-путь не видит при кодировании. Оставлено opt-in. Следующий шаг: выгрузить гостевые байты BC3 156x72 (`KYTY_SMALL_TEX_DIR`-подобный дамп) и декодировать офлайн с разными tile/форматами; найти, кто пишет источник копии (`KYTY_TRACE_RANGE=<lo>,<hi>`).
**A/B um73 (всё включено) / um74 (`KYTY_GUEST_TEX_NO_REFRESH=1 KYTY_ALIAS_NO_OLD_WRITER=1`, до правки opt-in):** в обоих есть красная комната с растянутыми по горизонтали объектами/осколками от игрока, белые кадры, бирюзовые шары света у ног игрока; um74 показал больше сцен (FC News над красной комнатой с игроком и мячом, The Grounds с игроком в синем, улица с игроком в красном) — разброс сцен между прогонами по-прежнему больше эффекта правок.
**Открытые вопросы по 3D (приоритет):** (1) инициализация HDR-цели G-buffer RT3 (`0x8245620000`): трасса `KYTY_PASS_TRACE_FLIPS=2` в 3D-сцене (детектор `THR=0.2`), найти очистку/проход неба в начале кадра; (2) бирюзовые шары = насыщенные пиксели (вероятно мяч/голова игрока; у эталона на голове игрока тоже синее свечение — общая ошибка фронтенда?); (3) растянутые по горизонтали объекты в красной комнате (вершины).

## Дополнение 2026-11-02 (Opus, день): сверка с Vulkan-путём, скорость 18–21 → 30–37 FPS в матче
**Уточнение к прошлому выводу.** `KYTY_CLEAR_HDR_FIRST` очищал цель только когда она RT0 (проход освещения), т.е. *после* прохода G-buffer, — «чёрное небо» не доказывает, что небо не пишется. 1. Пустые слоты изображений: все 1196 (`KYTY_LOG_UNBOUND=1`, `[Unbound]`) — **нулевые T#** (Base40=0, 2D). Vulkan даёт им пустую 1x1 (нули, как AMD), Metal подставлял **белую** 4x4. `KYTY_UNBOUND_ZERO=1` — нули (opt-in, визуально пока не оценено; кандидат в умолчание).

## 2026-11-02 (night, Claude um112–um126): white frames = sampled DCC layer cleared only through its metadata

**Cause.** The white/noise full frames (~30% of menu shots) came from the half-res transparency composite `ps=0x125da093168cba50` (tint × texture, premultiplied blend over the full-res scene). Its T# (872x492/800x452 RGBA16F, tile 27) has META_COMPRESS (dword6 bit 21) and a metadata address (dword7<<16). The game never renders that layer: it "clears" it by a uniform-fill kernel over the DCC metadata (e.g. `cs=0xee7822dc…` 16 KB at the meta address right before the composite), so on hardware every block reads as the clear colour (code 0x00 → 0). We read the raw pixel memory, which belongs to whatever transient surface lived there (G-buffer RGB10A2, scene copy R11G11B10, CoC RG16F): NaN / ±65504 → bloom → white. Same on the Vulkan oracle (its sheet has white menu frames too).

**Ruled out on the way:** compute-write race (`KYTY_MTL_SYNC_EACH=quiet` still white), strict waits (`KYTY_WAIT_RETRY_ELIDE=0 KYTY_WAIT_BY_ORDER=0 KYTY_LABEL_FLUSH=always`), CPU run-ahead (new `cp_lag` PassTrace line: the CP is 4–7 graphics submissions behind, under half a frame), CP writes into the descriptor ring (`KYTY_LOG_CP_WRITES`: none), COND_EXEC/predication/conditional IB (new `KYTY_LOG_COND`: the game uses none in the menu), previous-frame reuse (three consecutive traced frames: stable addresses).

**Fix (metalRenderer.mm, `SampledMetaClear`).** Every recognised uniform fill is remembered (`s_meta_fills`, by address, with a sequence number); colour passes, depth passes and compute storage writes stamp the surface (`s_rt_pass_seq`, `NoteSurfaceWrite`). A sampled image with META_COMPRESS whose metadata lies in a fill newer than the image's last write is replaced by a cached texture of its size/format filled with the clear colour (codes 0x00/0x40/0x80/0xc0; 0x20 only when a render target registered that metadata). Depth formats are excluded (HTILE has its own path). `KYTY_NO_META_CLEAR=1` disables it with the rest of the meta-clear logic. um126: 2 washed-out shots of 42 (was ~30%), the 3D menu scenes (red room, stadium, alley, street) show every cycle.
