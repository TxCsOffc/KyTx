## Что изменено

Найденная сессия Claude остановилась перед временной защитой TAA и исследованием памяти. После уточнения пользователя защита TAA полностью удалена: четыре затронутых файла восстановлены побайтно из копий до эксперимента, новый заголовок удалён, основной и тестовый исполняемые файлы пересобраны/обновлены. Нового обнуления NaN, пропуска шейдеров или подмены ресурсов в итоговом патче нет.

Вместо этого исправлены два пути создания **линейных** видов гостевой памяти:

- `GpuSurfaceFor` теперь получает буфер через `MetalBufferManager::GetBufferForGuestRange`, вместо отдельного `WrapHostMemory` по виртуальному адресу.
- Такой же путь используется для buffer-backed render targets.
- Повторное использование текстуры проверяет текущий буфер, физическое смещение, шаг строки, размер и формат. Одинаковый виртуальный адрес после remap больше не является достаточным условием.
- При замене вида удаляется запись последнего GPU-писателя, если она указывает именно на заменяемый объект.
- Поколение отображений памяти входит в совместимость открытого render pass: после изменения mapping повторная проверка ресурсов не обходится ранним `return`.

Это ограниченное исправление идентичности backing. Оно не является завершённой системой согласования всех текстур и не доказывает устранения игровых артефактов.

## Воспроизводимый дефект

Независимый тест создаёт две страницы одного файла, отображает гостевой адрес на первую страницу, создаёт Metal-обёртку, затем переназначает тот же адрес на вторую страницу. Все GPU-операции завершаются перед remap: гонка здесь исключена.

На этом Mac результат следующий:

| Чтение после remap | Полученное значение |
|---|---:|
| CPU через гостевой адрес | `2468ace0` — новая страница |
| GPU через прежнюю Metal-обёртку | `13579bdf` — старая страница |
| GPU через backing-буфер с новым физическим смещением | `2468ace0` — новая страница |

Новый регрессионный тест дополнительно выполняет запись через новую GPU-текстуру. CPU видит записанное значение через remapped alias, первая физическая страница остаётся прежней. Проверяются идентичность буфера, смещение, stride, extent, формат и границы выделения.

До исправления `s_rt_cache` проверял адрес/формат/размер; `s_gpusurf` — адрес/размер/формат/stride. Соответствие нового mapping старой обёртке не проверялось. В самом `MetalBufferManager` уже существовали физические чанки и перепроверка mappings; теперь эти два пути поверхностей используют их.

## Можно ли реализовать AMD tiling на Metal

Да. В проекте уже есть GPU-функции `EncodeTileImport` и `EncodeTileExport` в `src/graphics/host_gpu/metal/metalTiling.mm`. Они используют целочисленные представления элементов, чтобы сохранять биты, а не преобразовывать числовой смысл пикселя.

Проверка `tools/test_metal_tiling.sh` прошла: **58 вариантов раскладки, 0 ошибок; 8 mip-цепочек, 0 ошибок**. Там же проверяются экспорт mip-tail и сохранность незатронутых байтов. Эталон этих тестов — адресация из `guest_gpu/tile.cpp`, а не независимый захват с PS5. Таким образом проверена согласованность реализации в проекте, но не полная совместимость со всем оборудованием Sony.

Metal поддерживает текстуры поверх буферов, но этот API задаёт линейный stride; это не способ задать AMD swizzle. Нативный текстурный объект Metal также не становится AMD-текстурой из-за `storageModeShared`. Ограничения и правила видимости описаны в [документации Apple для buffer-backed textures](https://developer.apple.com/documentation/metal/mtlbuffer/maketexture(descriptor:offset:bytesperrow:)).

Два рабочих варианта: GPU import/export между раскладками или вычисление AMD-адреса непосредственно в MSL при обращении к буферу. Второй путь требует собственной реализации фильтрации и выбора mip для тех операций, которые раньше выполнял texture sampler.

DCC/CMASK/HTILE и fast clear требуют отдельного учёта метаданных. Перестановка байтов не реализует семантику сжатия или очистки. В коде есть частичные обработчики metadata clear; считать это полной эмуляцией этих механизмов нельзя.

## Где остаётся архитектурная проблема

Проверено по исходникам:

1. `CpOpAcquireMem` в `guest_gpu/command_processor/pm4Handlers.cpp` проверяет заголовок и пропускает payload. Диапазон и cache actions не передаются модели памяти.
2. `CommandProcessor::EmitGlobalBarrier` в `graphicsRun.cpp` сразу возвращает для Metal. Это само по себе не доказывает отсутствие GPU-порядка: в Metal-пути уже есть encoder fences. Но PM4 cache actions не управляют согласованием отдельных копий данных.
3. Реестры `s_cs_storage`, `s_guest_textures`, `s_aliased_images`, render-target и layered/mip caches имеют разные ключи и правила актуальности. Некоторые решения зависят от числа прошедших flip, а не от записи в память.
4. `AliasConvert` экспортирует писателя в scratch-буфер и импортирует потребителя из него. Это отдельное преобразование между представлениями; оно не делает каноническую гостевую память актуальной для любого последующего raw-buffer/CPU-чтения.
5. Два разных виртуальных адреса могут ссылаться на одно physical backing. Поэтому общего трекера только по виртуальным страницам недостаточно.
6. `GuestTexSourceHash` для источников больше 64 КиБ проверяет четыре окна по 512 байт. Это эвристика: запись вне этих окон может остаться незамеченной. Она не заменяет точный учёт dirty-диапазонов.

Эти факты не доказывают, что все ошибки изображения вызваны памятью. Перевод RDNA→MSL, форматы, depth/stencil, геометрия и синхронизация должны проверяться отдельно.

## Предлагаемая модель

**Одна логическая память, несколько согласованных представлений.** Канонический ключ — physical backing и смещение с учётом mapping generation. Нативная текстура может временно владеть самой свежей версией; не требуется копировать её в гостевые байты после каждого draw.

На диапазонах необходимо хранить sequence записи, владельца актуальных данных, раскладку и версии зависимых представлений. Страницы по 16 КиБ подходят для поиска пересечений на этом хосте, но внутри страницы нужен учёт поддиапазонов: один счётчик на страницу не разрешает частичные записи и соседние ресурсы. Mip-tail, слои и metadata тоже входят в зависимости.

Правила доступа:

- Потребитель того же представления использует актуальный объект напрямую.
- Другому представлению сначала предоставляются актуальные байты в требуемой раскладке; преобразование кодируется в GPU-порядке.
- Raw buffer или CPU получает экспорт dirty-текстуры, когда ему нужны именно гостевые байты.
- Частичная запись сохраняет незатронутые данные; размер writable-дескриптора не доказывает запись каждого байта.
- CPU/DMA/GPU-запись инвалидирует пересекающиеся устаревшие представления, включая aliases другого виртуального адреса.
- Cache invalidation, завершение GPU и видимость для CPU различаются. Их нельзя заменить одним безусловным CPU wait.

Следующий этап: декодировать реальные и внутренние варианты PM4 acquire/release, добавить трекер диапазонов сначала в режиме проверки и подключить одну воспроизводимую цепочку producer→consumer. Затем расширять его на raw buffers, metadata, mips и CPU-visible releases.

Основание для правил порядка: [Apple Resource synchronization](https://developer.apple.com/documentation/metal/resource-synchronization) и [CPU/GPU dependencies](https://developer.apple.com/documentation/metal/synchronizing-cpu-and-gpu-work). Для общего механизма AMD acquire/release: [открытый драйвер AMD PAL, gfx9CmdUtil.cpp](https://github.com/GPUOpen-Drivers/pal/blob/dev/src/core/hw/gfxip/gfx9/gfx9CmdUtil.cpp). PAL описывает семейство AMD, а не все особенности закрытого GPU PS5; точное соответствие Sony требует отдельных проверок.
