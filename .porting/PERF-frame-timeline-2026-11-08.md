# Что ограничивает время кадра: гостевой CPU (FEX), командный процессор KyTx (CP) или GPU

Дата: 2026-11-08. Сцена: титульный экран EA FC 27 (idle), игра сама ставит `sceVideoOutSetFlipRate(1)` = 30 Гц. Ветка `metal-native-checkpoint`, M5 Max, нативный Metal.
Все цифры ниже получены тремя запусками `idle_repro.sh` (t1, t2, t3, по 3 минуты). Сырые данные: `.porting/work/out/t1|t2|t3/` (локально, не публиковать: рядом лежат скриншоты игры).

## 1. Вывод (коротко)

1. **В этой сцене кадр ограничивает не один из трёх ресурсов, а 30-герцовый лимит флипа игры.** Ни гостевой CPU, ни CP, ни GPU не насыщены: в «чистой» конфигурации (t3) на кадр 33,33 мс приходится: самый загруженный гостевой поток 6,0 мс CPU (18 % ядра), CP 5,3 мс CPU (16 % ядра, активное окно ~16 мс по стенным часам), GPU 8,5-14,2 мс (HUD; 26-43 % интервала). FPS 30,00 при 59 из 60 строк `[rate]` (единственное исключение - конец прогона).
2. **FEX / гостевой CPU на критическом пути, ограничивающем FPS, в этой сцене НЕ стоит.** Все гостевые потоки вместе дают 31,8 мс CPU на кадр (0,95 ядра), и примерно 60 % из них - цикл опроса часов (`KernelGetProcessTimeCounter` + заглушка + `LastCallEnter`), то есть ожидание, а не работа. Настоящий гостевой JIT-код ~0,24-0,29 ядра (~8-10 мс CPU на кадр суммарно по 6 воркерам). Ускорение или замедление FEX вдвое на этой сцене кадр не изменит.
3. **Самая важная находка по методике: слой GPU Frame Capture (`MTL_CAPTURE_ENABLED=1`, жёстко прописан в `KyTxMetalS1.app/Contents/MacOS/launch`) искажает все прежние замеры.** С ним CP-поток занимает 21,8 мс/кадр (65 % ядра), без него 5,3 мс/кадр (16 %); весь процесс 81,7 против 45,4 мс CPU на кадр; GPU по HUD 22,3 мс против 8,5-14,2 мс. Прежние профили (`r11`, `r12`, `t1`, `t2`) показывают в основном этот слой, и именно с ним CP выглядел «узким местом» (в `t2` даже были провалы до 27-28 fps, в `t3` их нет). Для любых замеров производительности нужен `EXTRA_ENV="MTL_CAPTURE_ENABLED=0"` (проверено отдельной программой: значение 0 слой выключает).
4. Ранжирование нагрузки в этой сцене (чистая конфигурация): GPU (26-43 % интервала) > самый нагруженный гостевой поток (18 %) ≈ CP (16 %). Если бы лимит 30 Гц сняли, первым упёрся бы, судя по загрузке, GPU, но это экстраполяция, не измерение.
5. Для матча решение по FEX по этой сцене принимать нельзя (титульная сцена лёгкая и зажата лимитом). Нужен тот же замер в матче, протокол и пороги в разделе 8.

## 7. Метод

1. `idle_repro.sh <tag> 3 1000` (PassTrace выключен), параллельно мой наблюдатель `perf_frame_watch.sh` (только читает, процесс не запускает и не останавливает): каждую секунду `ioreg` AGX Utilization; каждые 3 с `ps -M` (накопленное CPU по потокам) и HUD-цифры (скриншот окна, OCR tesseract только по области HUD, файл сразу удаляется); временные метки строк `[rate]`/`[GpuPass]` лога; в момент ~60 с после появления процесса - 25-секундная запись `xcrun xctrace record --template 'Time Profiler' --attach <pid>`.
2. Экспорт таблицы `time-profile` в XML, разбор `perf_tp_parse.py`; категории `perf_tp_breakdown.py`; свёртка по фазе флипа `perf_fold.py`; окна и `ps -M` - `perf_window.py`, `perf_psm.py`, `perf_timeseries.py`. Прежний разбор `sample` - `perf_sample_parse.py`, `perf_sample_tree.py`.
3. Роли потоков по стекам: CP - содержит `GuestGpu::ThreadRun` / `CommandProcessor::Process`; поток флипов - `VideoOutDriver::Impl::PresentThread`; гостевые - кадры JIT-адресов / `kyty_fex_host_call` / `Loader::GuestCpu`; Metal-отправка - `iokit_user_client_trap`.
4. Слой захвата отключён значением `MTL_CAPTURE_ENABLED=0` из `EXTRA_ENV` (лаунчер сначала ставит 1, затем выполняет `extra_env_s1.sh`, значение перекрывается). Проверка: маленькая программа Metal показала, что при 0 и пустом значении `GPUToolsCapture` не загружается, при 1 - загружается.

## 8. Как установить факт в сцене матча (когда пользователь сможет играть)

Тот же набор, в матче, тег любой (лимит в 3 запуска относился к этой задаче):

```
cd /Users/tx/Developer/KyTx/.porting/work
PROF=xctrace ./perf_frame_watch.sh m1 <t_с_появления_процесса_до_геймплея> 25 hud &
EXTRA_ENV="MTL_CAPTURE_ENABLED=0" SCRIPT=<скрипт_ввода_в_матч> ./idle_repro.sh m1 4 1000
# потом: xctrace export ... time-profile -> perf_tp_parse.py -> perf_tp_breakdown.py / perf_fold.py (роли потоков ищутся так же)
```

Решающее правило (по xctrace на окне 25 с в установившемся геймплее, плюс HUD):

| Что видно | Узкое место |
|---|---|
| Интервал кадра > лимита (33,3 мс при 30 fps), какой-то гостевой поток ≥ 85-90 % ядра на всём окне, CP < 60 %, HUD GPU < интервала минус 3 мс | гостевой CPU (FEX) |
| CP-поток ≥ 85-90 % ядра, гостевые потоки < 60 %, HUD GPU < интервала | CP KyTx |
| HUD GPU ≈ интервал (минус 2 мс), (AGX util - фон 36 %) близко к 100 % | GPU |
| Никто не выше ~70 %, но кадр длинный | зависимость/ожидание (синхронизация); нужны состояния потоков |

Чего в моих данных не хватает, чтобы закрыть вопрос полностью (что стоит добавить):
1. Причины ожиданий CP (ждёт гостя, ждёт GPU, ждёт `WaitRegMem`): Time Profiler их не видит. Либо `xctrace` с шаблоном System Trace (состояния потоков и «кто разбудил»), либо счётчики в коде: на каждый флип логировать наносекунды «CP занят», «CP ждёт следующий сабмит», «CP ждёт GPU/метку», время сабмита гостя, время `GPUStartTime/GPUEndTime` первого и последнего command buffer кадра, момент флипа. Код я не менял, это предложение.
2. Имена хостовых потоков: вызывать `pthread_setname_np` в `PthreadRename` - тогда главный/рендер-поток гостя будет виден в профиле по имени.
3. Metal System Trace (Instruments) на 5-6 с - реальные интервалы GPU по кадру.
4. Для проверки «насколько FEX на пути» в матче: суммарный CPU гостевых потоков, доля настоящего JIT-кода (без цикла опроса часов) и доля рантайма FEX (компиляция при первом заходе в код; прогреть кэш).

## 9. Ограничения

- Сцена: титульная, зажата игрой на 30 Гц, FPS разных запусков не сопоставимы (использованы доли времени внутри одного запуска). Загрузка потоков в матче будет другой.
- Один запуск на конфигурацию, разброс между запусками неизвестен. t2 и t3 различаются слоем захвата и моментом внутри цикла титульной сцены (HUD GPU 8,5 против 13,3-14,2 мс внутри самого t3); окно CPU 25 с начинается в конце первой фазы и в основном покрывает вторую. Отношение CP 65 % к 16 % значительно больше любого такого разброса.
- Metal HUD (`MTL_HUD_ENABLED=1`) оставлен: он нужен для «GPU ms». Метрик-хук HUD (`libMetalMetricsInterpose`, `FramePacing`) остаётся в стеках CP и даёт часть стоимости драйвера в t3.
- Time Profiler показывает только время на CPU, не стенное время и не ожидания. Окно «ждёт ~60 %» в CP - вывод по недогрузке, причина ожиданий не установлена (в искажённом `sample` t1 87 % ожиданий CP приходилось на ожидание следующего сабмита гостя, 4 % - на Metal).
- Утилизация AGX из ioreg включает композитор и остальные приложения (фон 36 %), HUD «GPU ms» - собственное время GPU приложения.
- HUD читался OCR; строки с нечитаемым значением отброшены. Значения HUD - мгновенные на момент скриншота (раз в 3-4 с).
- Распределение «заглушка/цикл опроса» по странице JIT-кода - вывод по стекам, а не по символам.

## 10. Побочные находки (не по основной задаче)

- В гостевых воркерах ~22 % CPU уходит в `SysQueryPerformanceCounter` (`clock_gettime` -> `gettimeofday` -> `mach_absolute_time`), ещё ~10 % - в `LastCallEnter`. Удешевление этого пути (прямой `mach_absolute_time` + масштаб, отключаемый `LastCallEnter`) вернуло бы до ~0,3 ядра на гостевую часть; на FPS в этой сцене не влияет.
- 5 потоков отправки Metal суммарно 7 мс CPU на кадр (в t3): примерно столько же, сколько сам CP.
