## Главные находки сегодня

### 1. Эмуляция wave64 для compute — самое сильное улучшение
`KYTY_MSL_WAVE64=1` (`MslEmitter.cpp`: `Wave64Pair`, один 32-канальный simdgroup обслуживает обе «половины» 64-канальной волны RDNA). Причина: RDNA-ядра рассчитаны на одну 64-канальную волну (LDS без барьеров в lockstep, cross-lane операции по 64 каналам); в Metal группа из 64 потоков — два независимых simdgroup по 32. Редукции яркости/bloom/гистограммы на LDS давали NaN, полосы, шум.

Результат без других изменений: `.porting/artifacts/2026-10-27/uh2/*.ppm` (14 кадров, флипы 3347…9009), `uh3` (кадры + дамп промежуточных картинок на 13 present). Улицы теперь связные: перспектива, окна, мягкое затенение; кадр 3347 — готовое меню «FC NEWS / Welcome to the Club!». До этого каждый билд давал шум и потоки.

Что осталось и в wave64-only режиме:
- пересвет и bloom-размытие по горизонтали (на 100% разрешения картинка мыльная, горизонтальный смаз);
- материалы без текстур: белые/плоские полигоны (default white texture);
- полосы «жалюзи» по строкам в освещённом HDR (`rt0x8242360000` RG11B10, max 368);
- чёрные кадры (5519, 5950, 6385, 9009 в uh2);
- стабильность: ранее фиксировали ~25% падений в загрузке с включённым wave64 (guest-указатели). Последние запуски uh2/uh3 (300 с, до флипа 9100) прошли без падения, uh1 (150 с) просто не дошёл до меню (с wave64 флипы идут медленнее). **Нужен замер на 5–10 запусках, прежде чем делать default-on.** Бисекция при падениях: `KYTY_MSL_WAVE64_RANGE=lo,hi` по `(hash>>4)&255`.

### 2. Источник NaN в проходе освещения найден (идентичность поверхности)
Pass-trace (`uh4`, кадр 4335): draw n=291, PS `0x944430b5642a46c5` (VS `0x69d70c650eb2f56b`, пишет RT0 `0x8249960000` и RT1 `0x8242360000`, оба 1616x912 RG11B10) читает вход slot64 `0x824a660000`, T# 1616x912 tfmt=36 (RG11B10, tile 9) — а последний писатель по реестру: **текстура 1600x904 R32Float прошлого кадра**. Поиск по реестрам (`LastGpuWriterTexture`: `last.width == w && last.height == h`) не находит совпадения → падает в `ComputeGuestImage` (копия нетронутой гостевой памяти) → NaN (24381 NaN во входе). Дальше NaN растёт в RT (nan=26976 inf=401).

Правда о поверхности: по правилам тайлинга pitch = `AlignUp(width, block_width*texel_width)` (`TileGetTexturePitch`, tile.cpp:1337): 1600 и 1616 дают одинаковый pitch (1664 текселя для 4-байтовых) и одинаковую выровненную высоту. То есть это **одна и та же поверхность**, T# описывают видимую область. Поверхность определяется адресом + выровненной раскладкой, а не размером дескриптора.

### 3. UMA-поверхности (`KYTY_UMA_SURFACES=1`, по умолчанию выкл.)
GPU-созданные картинки — линейные view поверх гостевой памяти (`GpuSurfaceFor`, `WrapHostMemory` + `CreateTextureView`); RT уже были такими. Таблица «GPU писал» теперь по **точному стартовому адресу** (`GpuWriteStamp`, возраст ≤4 флипа) вместо склеенных диапазонов (склеенные ломали тайловые CPU-текстуры внутри RT-пулов: читались как линейные → цветной шум, см. `ud1`/`ug1`). `KYTY_UMA_RANGE=overlap` возвращает склеенные диапазоны для сравнения.
Графический сэмплинг идёт через ту же таблицу (`GraphicsImageFor`, ветка в начале; только plain 2D, без mip/глубины; `KYTY_LOG_UMA=1` логирует `[UmaGfx] … match=exact|overlap`).
**Последняя правка (собрана, проверена только до запуска): `GuestViewRowBytes`** — строка view = гостевой pitch × bpp (с выравниванием Metal ≥64), и для RT-view, и для `GpuSurfaceFor` (теперь принимает `Prospero::TileMode`; ключ кэша включает row bytes). Это должно свести 1600x904-дескриптор и 1616x912-RT одной поверхности в одни и те же байты. `KYTY_UMA_PITCH=tight` — старое правило (видимая ширина) для сравнения. **Эффект на картинку этой правки ещё не увидели:** запуски с ней (`uj1`, `uj2`) упёрлись в GPU-watchdog (ниже).

### 4. Зависание под UMA + wave64 (не решено, главный блокер UMA)
`ui1`, `uj1`, `uj2` (UMA + wave64): GPU-watchdog (>20 с на одном command buffer) в загрузке, флип 1300–1590. Без UMA (uh2/uh3) зависаний не было. Watchdog теперь печатает список операций зависшего command buffer (`KYTY_MTL_GPU_TIME=1` включает метки): в `uj2` буфер содержал ядра `7cfddbf27fb2cf36`, `57468b708966ce18`, `61b4e525c59b550e`, `4a2058f38754a0a5`, `0122e6902be1a23a`, `938a121888afce63`, `fb2f886f2cc4c087`, `1b2e59f349e21b76`, `38dd66287e3b3c9d`, `2f4dadde068a486e`, indirect-dispatch'и и draw'ы с PS `944430b5…`, `dcb17fca…`; точный виновник не определён (раньше подозревали `66224a22378c016e`). Запуск пошагового трейса (`uj3`, каждый dispatch/draw отдельно, тогда watchdog назовёт единственный op) был прерван при сворачивании сессии на флипе 675 — повторить.

### 5. Остальное, что известно из дампов
- Albedo/G-buffer при wave64 чистый (`rt0x8241050000 1624x912 f71`: фасады, вывески, асфальт), нормали (`0x82409d0000` RGB10A2) выглядят как нормали. Ломается освещённый HDR: `cs/rt 0x8242360000` (RG11B10): пересвет + полосы; выше по цепочке — NaN из п.2.
- Адрес `0x8242360000` используется и как compute-store (`cs 44c8d0b4ea6e280c`, RGBA8 1600x904) и как HDR-RT 1616/1624x912 в разных MRT-слотах (3,3,0,1) — один адрес, много поверхностей в кадре; это алиасинг transient-памяти Frostbite.
- Результаты прошлых UMA-экспериментов (без wave64): пара ядер `a7baaba4a9d24ae8`+`6ef6812b13b47318` давала тёмную чистую сцену (`ub6`), все ядра сразу — белые кадры, раздельно — как базовая линия.
