## Fixed this session
1. **Memory leak (50-100 GB/instance)**: pointer-keyed view caches (`s_fv` ReinterpretFormat, `s_swz_views`, `s_views`, `s_arr`) kept every texture alive forever (a view retains its parent). Now stamped with the flip counter and swept (`SweepViewCache`, 90 flips); depth/stencil per-address surfaces swept after 120 flips; autorelease pool per GPU slice (`graphicsRun.cpp`). Flat 8.2 GB through flip 2600, live AGX textures 21k -> 3.5k. Diagnostics: `KYTY_MEM_LOG=1` ([Mem] line with cache sizes, top allocators by shader, allocations by source line).
2. **Window title update** no longer blocks the flip thread on the SDL main thread (async, one in flight).
3. **3D guest textures were created EMPTY** (`GuestTexture3D`): the colour-grading LUT generator (cs `8cc0d51128a51513`) samples guest volumes, so every graded LUT came out constant and the composite (ps `691682abac626839`) was black. Now tiled volumes are decoded (`DecodeTiledVolume`, metalTiling.mm) and uploaded, refreshed on content change; RG11B10 volumes are widened to RGBA32F. Result: composite output is no longer constant; the frame shows scene structure but is green/noisy (see open items).
4. `MslEmitter`: wave64 pair-pack (`KYTY_MSL_WAVE64=1`, `KYTY_MSL_WAVE64_RANGE=lo,hi` on `(hash>>4)&255`) stays OFF by default (about 1 in 4 launches crash in the loading window when on).
5. Shader compile mode: `KYTY_MSL_MATH=safe` is the default now (fast-math off); it changed nothing visible.

## Diagnostic tools added (all env-gated)
- `KYTY_PASS_TRACE_TRIGGER=<file>`: one frame, every compute dispatch and every draw runs alone; `[PassTrace]` lines with NaN/Inf/min/max (+ per-channel with `KYTY_PASS_TRACE_CHANNELS=1`) of float RTs and storage images (also 3D volumes), `KYTY_PASS_TRACE_INPUTS=<ps hash>` adds that draw's sampled images with T# and its constant buffer dwords. `work/fliptrigger.sh <pid> <tag> <log> <first-flip> <step>` fires it by flip count (menu stage is flip >= 3800 with KYTY_AUTO_INPUT).

- Root-cause class found: **transient guest memory is aliased heavily within a frame** (the same address is a 1776x1000 f56 image, a 3072x1080 f250 depth/stencil, a 960x540 f55 image, an RG11B10 RT... at different times) and tiled compute images are separate Metal textures chosen by last-writer / size / format heuristics (`LastGpuWriterTexture`, `GetComputeWrittenImageForAddress`, `AliasedImageFor`, `AliasConvert`, `GuestTexture`). When a heuristic picks the wrong object a pass reads zeros/NaN, which explains randomness and growth over time. A robust fix is a surface table keyed by memory range (one backing store per live byte range, views per (format,size)) instead of per-address heuristics; not started.

## Update 2026-10-27 (Claude, aliasing investigation)
Fixed (all in `metalRenderer.mm`, default-on, no env):
- **Pass size for flipped viewports**: `EnsureActiveRenderPass` and `NativeColorLayout` fell back to 1080 when `viewport.yscale` was negative (flipped Y), so depth-only passes (shadow maps, half-res depth) got e.g. 812x1080 instead of 812x456 and consumers of that depth never found it (-> read zeros/garbage). Now `fabs(scale)`.

The luminance pyramid kernels (f3ccd962..., 9358d7e5..., d945de35..., cce5f44e..., 29696d31...) write mip levels of the HDR target; the mip views bind correctly in this build (`[CsMip]` lines: levels 1..6 bound_view=1). ## Update 2026-10-27 (Claude): GPU-produced compute images as guest-memory views (opt-in)
- `GpuSurfaceFor`/`NoteGpuWrite`/`GpuWrittenOverlaps` in `metalRenderer.mm`: compute storage images (plain 2D, single level, writable format) and sampled images of GPU-written ranges can be linear buffer-backed views over the guest pages (same pitch rule as the RT views), render-target passes record their ranges. **Opt-in: `KYTY_UMA_SURFACES=1`** (bisect with `KYTY_UMA_ONLY=<hash prefixes>` / `KYTY_UMA_SKIP=<...>`; `work/uma_run.sh <tag> <all|-|skip:..|prefixes> [secs]` runs one instance and prints the mean luma of frame dumps).

Producer/consumer pairs must both use the memory path or the reader sees stale data, which is why partial enabling looks random.

## Update 2026-10-27 (Claude): wave64 pair lowering is the biggest single improvement so far
- `KYTY_MSL_WAVE64=1` (compute wave64 emulated as one 32-lane simdgroup handling both halves; MslEmitter `Wave64Pair`) with NO other change: `artifacts/2026-10-27/uh2/*.ppm` (flips 3347..9009, 14 dumps). Street scenes now have coherent perspective, smooth shading, correct building/window layout and the menu text (frame 3347 shows "FC NEWS / Welcome to the Club!" fully composited). Without it every build so far gave noise, vertical/horizontal streaks and flat green. Remaining in uh2: scene still over-exposed/bloom-smeared, material textures look missing (plain white/flat shaded polygons), some frames black (5519, 5950, 6385, 9009), horizontal "venetian blind" row striping on top of the picture. Run took 300 s without a crash (the earlier note said ~1 in 4 launches crash in the loading window with it on; re-measure before making it default).
- Reason: RDNA compute kernels assume one 64-lane wave (lockstep LDS use without barriers, cross-lane ops over 64 lanes); on Metal a 64-thread group is two 32-lane simdgroups that do not run in lockstep. All the luminance / bloom / reduction kernels that produced NaN and streaks use LDS and lane ops.
- UMA experiments of the same day (see above) `ud1`/`ug1`/`uf1`: graphics sampling through the GPU-written table (`KYTY_UMA_SURFACES=1`) gives structure + coloured noise when ranges are merged (`KYTY_UMA_RANGE=overlap`: tiled CPU textures inside RT pools are misread as linear), baseline-like green wash with exact-start matching (default now). `KYTY_LOG_UMA=1` logs `[UmaGfx]` reads with match=exact|overlap. Tools: `work/img_run.sh <tag> <uma 0|1> [secs] [first-flip]` (env `RANGE=overlap`, `EXTRA="K=V ..."`), `work/dumpsheet.py <log> <present> <out-prefix>` (labelled contact sheets of the `KYTY_DUMP_IMG=all` intermediates with the compute kernels that write each image).
