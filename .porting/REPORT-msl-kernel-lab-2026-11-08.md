# Лаборатория MSL-ядер KyTx: насколько хорош сгенерированный MSL для GPU Apple (2026-11-08)

Автор: субагент (текст сохранён главным агентом). Железо: Apple M5 Max, macOS 27.2. Эмулятор агентом не запускался (параллельно работал `kyty_emulator_s3` другого агента, CPU ~30%, GPU общий). Существующие исходники не менялись. Игровые данные (MSL, дампы буферов) в отчёт не копировались.

ВАЖНО: доли GPU-времени ядер (7.9%, 5.3% ...) сняты профилировщиком проходов при включённом слое Metal frame capture (см. `PERF-frame-timeline-2026-11-08.md`); доли могли сместиться. Измерения самой лаборатории (микро-бенчи ядер) от слоя не зависят.

## Кратко
1. Главная потеря GPU-времени: wave64-«пара» (2 guest-лейна на нить, `_h`-дубликаты). Те же 64 лейна как 64 нити (2 simdgroup, половина `_h` убрана; верхняя оценка, без барьеров): время x0.38 (5d0d), x0.44 и x0.53 (e5288, два набора РЕАЛЬНЫХ буферов), x0.87 (c4bb), x0.35 (a170, путь не проверен). Выход половины лейнов побитово тот же (e5288: 40570 из 40570 слов; 5d0d: 524288 из 524288 текселей).
2. Bounds-check: -8..-9% на e5288 (реальные данные, оба набора), -7% на 0ef4, на остальных в шуме. Выход тот же, проверки на реальных данных не срабатывали. Компиляция быстрее на 15-30%. Итого ~0.6% общего GPU.
3. `kyty_ftz`: -1..-4% (5d0d до -10%, шумно), выход побитово тот же.
4. Fast math: -3..-14%, но результат МЕНЯЕТСЯ (e5288 ~2% слов, c4bb 23 текселя). Fast только для функций (fnfast): -3..-9%, тоже меняет. Не включать.
5. Находка: KyTx реально компилирует MSL как язык 3.0: `#if defined(MTLLanguageVersion4_0)` ложно (enum, не макрос; проверено на этом SDK, `-D` в compile_commands нет). Язык 4.0 на время и регистры не влияет.
6. `maxTotalThreadsPerThreadgroup` = 1024 у всех 9 ядер: на M5 как индикатор давления регистров бесполезен. Различает только тайминг.
7. Шум измерений ±5% (по контролю l40, идентичный код).
8. Рекомендация: A/B через уже существующий `KYTY_MSL_WAVE64_SKIP=<host hash>` на 5d0d6f16bddf8cad, edbcd7e4f0579e83, e5288af74a34533b, a170bb86d24a6f2a; при целой картинке выделить класс ядер без межлейновых операций и LDS-обмена между половинами (иначе 64 нити + threadgroup_barrier). Потенциал до ~6% общего GPU (верхняя граница). Bounds-check снимать только для константных индексов при гарантированном хостом размере (<1% GPU). ftz и precise math не трогать.
9. Не удалось: 3ad95c14ba036b6e (7.9%) нет ни в одном дампе; PS 090e154f только компиляция библиотеки; 78d2, a170, 30caea на синтетике не удержать на рабочем пути (охрана циклов 8192 или пустой путь); 30caea на реальных данных почти пуст (2-3 валидные нити из 256).

Качество кода для GPU:
- Одна плоская функция, все значения объявлены нулём наверху, всё хранится как uint с `as_type<float>` на каждом использовании. LLVM это сворачивает, но стоит front-end времени: 24-27% операторов больших ядер это копии phi, 25-35% чистые bit-cast, 14-20% селекты по маске лейна.
- Пара: половина операторов это дубликаты `_h`. Доля лейн-равномерных операторов (`tools/bench/msl_uniform_share.py`): 0.3% (5d0d), 13% (e5288), 15% (a170), 8.5% (c4bb), 5% (30caea). Дедупликация uniform-значений ничего не даст, проблема в самой схеме 2 лейна на нить.
- Мусор вида `(0x10 == 0u ? 0u : ...)`, тройные маски `& 0xffff`: компилятор сворачивает, GPU не страдает.
- Bounds-check: `(idx < (sizes[N]>>2) ? ab.buffers[N][idx] : 0u)` и диапазонная форма для typed f16-загрузок; аналогично для LDS (`< 5632u`) и записей.
- ftz на входе почти каждой fp-операции (1050 в 5d0d), вход часто уже результат ftz-операции.

## 6. Не измерено и ограничения
- 3ad95c14ba036b6e: нет MSL. PS 090e154f: только компиляция (нужен render pipeline); статически 13.5 bounds на 1000 операторов, по аналогии с 0ef4 ожидание -5..-7%, не проверено.
- 78d2, a170 (кроме одного ориентировочного числа), 30caea: на синтетике ядро не удержать на рабочем пути. 78d2: циклы идут до охраны 8192 (61 мс не зависит от числа групп) или не выполняются (0.02 мс) в зависимости от заливки. a170: с float/rand заливкой 15 мс на 1024 групп (вероятно охрана), с small ничего не пишется. 30caea на реальных данных: валидны 2-3 нити из 256 (buf0[40]=2..3), 0.14 мс на 1024 групп, ядро почти пустое, его доля вероятно определяется числом dispatch'ей.
- noguard только по компиляции (-0..-20%, шум): на GPU не запускался, бесконечный цикл = зависание GPU.
- **Выход e5288 недетерминирован между процессами** (изменённых слов 80995 / 82616 / 122854 в трёх запусках одного набора): гонка в ядре (в лаборатории или в трансляции); `--compare` надёжен внутри одного прогона, это проверка здравого смысла, не доказательство. (Главный агент: кандидат на проверку как источник артефактов.)
- Эксперимент nosel (убрать обнуляющие селекты) матчится 106 раз на e5288 (-3%), выход меняется; не развивался.
- Параллельно шёл эмулятор: абсолютные числа завышены и шумят; шум по l40 до ±5% (у 5d0d до ±8%), разницы <5% не значимы.
- nohalf это текстовое преобразование (удалены операторы с `_h`, ballot/shuffle берут значение первой половины), собирается на 5d0d, edbc, a170, e5288, c4bb, не на 30caea. Вторая simdgroup повторяет те же лейны (верхняя граница выигрыша).
