## Корень найден (ночь 2026-10-28/29, uk29–uk38): метки EOP писались на CPU сразу

В логе `[eop] labels deferred=0 immediate=30458 gpu_labels=0 cpu_labels=30458`: **в Metal-ветке все end-of-pipe метки писались `memcpy` при разборе пакета** (`PublishEopLabel`, `graphicsRun.cpp`), то есть игра видела каждую отправку завершённой мгновенно, переиспользовала транзитную память (аргументы indirect, кольцевые буферы), а Metal ещё читал её. Аргументы, которые видело GPU, оказывались данными другого кадра (затёртые 0xFFFFFFFF / 1.0f / таблицы смещений / матрицы).

## Дополнение (вечер 2026-10-28, uk20–uk28): порядок операций, а не UMA

Добавлен счётчик срабатываний предохранителя (`[IndirectGuard] N indirect dispatches zeroed so far; last seq=… cs=… args=… raw=… covered by: …; memory now: […]`, печатает вотчдог-поток раз в секунду; в тесте `Indirect guard counter` проверяется). Результаты (все — plain, UMA+wave64, cap 4096, вотчдог 8 с, бинарник с предохранителем):

| Прогон | Режим | Сколько dispatch'ей предохранитель обнулил |
|---|---|---|
| uk20 / uk22 / uk23 / uk24 / uk25 | базовый, UMA вкл., 150 с | 0 / 36 / 238 / 129 / 34 |
| uk26 | `KYTY_UMA_PITCH=tight` | 7+ (затирание остаётся) |
| uk27 | **UMA выкл.** (`KYTY_NO_UMA_SURFACES=1`) | **333** (затирание есть и без UMA; «covered by: (no GPU surface)») |
| uk21 / uk28 | `KYTY_SYNC_ENCODERS=1` (CPU ждёт каждый encoder), 300 и 200 с | **0 / 0** |

Вывод: **виноваты не UMA-виды и не размеры поверхностей, а порядок выполнения GPU-операций.** Подтверждение содержимым памяти (uk26, uk27): в момент чтения на месте аргументов лежал фрагмент таблицы (`15360, 15372, 15384` — шаг 12; соседние ячейки продолжают ту же таблицу), а при последующем чтении (`memory now`) там уже настоящие аргументы (`0xb, 1, 1`). То есть подготовка аргументов (читает их) выполнилась раньше, чем их записал producer. Причина: `MetalBufferManager::GetBufferForGuestRange` создаёт отдельный `MTLBuffer` на каждую стартовую страницу (`m_page_cache[page_aligned]`), поэтому две операции над перекрывающейся памятью — разные Metal-объекты; плюс UMA-виды и сырые GPU-адреса в argument buffer'ах. Metal упорядочивает encoder'ы только по общему объекту, остальные могут перекрываться; PS5 выполняет пакеты строго по порядку, и игра на это рассчитывает (транзитные ресурсы делят память по времени).

**Исправление (написано, в игре НЕ проверено):** `src/graphics/host_gpu/metal/metalOrder.h` — `KYTY_ENCODER_FENCES=1`: каждый encoder общего потока по концу обновляет `MTLFence`, следующий ждёт его перед первой командой (на GPU, без ожидания CPU). Подключено: render/compute encoder'ы контекста (`metalDraw.mm`, `EndCurrentEncoder`/`SetActive*Encoder` в `metalContext.mm`), blit отложенных заливок, три encoder'а подготовки аргументов (`metalIndirect.mm`), тайлинг (`metalTiling.mm`). **Не подключены:** ~10 blit'ов в `metalRenderer.mm`, использующих общий командник (строки ~160, 453, 1137, 1200, 1813…), и encoder'ы презентера. GPU-тесты проходят с флагом и без него. По умолчанию выключено.

**Первое, что сделать в следующий раз (один прогон, 150 с, plain, UMA+wave64):** `hang_run.sh uk29 150 "KYTY_ENCODER_FENCES=1"` и сравнить число `[IndirectGuard]` с базовым (4 из 5 прогонов были ненулевыми, до 238). Ноль → сделать fence'ы включёнными по умолчанию (измерить FPS: M5 Max держит 30 в меню), затем довести остальные blit'ы. Не ноль → искать encoder'ы без fence'ов (blit'ы в `metalRenderer.mm`) и операции, выполняемые на CPU раньше GPU-работы (WRITE_DATA/DMA_DATA/COPY_DATA в `pm4Handlers.cpp`, `KYTY_LABEL_FLUSH=lazy`, `KYTY_WAIT_RETRY_ELIDE=1`, `KYTY_UMA_READBACK=1`).

**Про Vulkan-ветку (вопрос пользователя):** в репозитории уже есть Vulkan-рендерер (`src/graphics/host_gpu/renderer`), который расставляет явные барьеры (`ShaderWriteHazardBarrier`, `ShaderAccessBarrier`, `pipelineBarrier` в `renderCompute.cpp`, план синхронизации `bdaSyncPlan.h`/`bdaSyncControl.h` для сырых адресов). Он «просто работает», потому что Vulkan заставляет отслеживать зависимости явно. Metal-ветка этого трекера не повторяет; логику барьеров из Vulkan-рендерера (что чем записывается и читается) стоит перенести в Metal как явные fence'ы по ресурсам, а не только цепочку «все encoder'ы подряд». Правило проекта: без Vulkan/MoltenVK/SPIRV-Cross в продукте; читать исходники как справку можно, код не копировать.

**Full HD (просьба пользователя):** `ConfigOptions` по умолчанию теперь 1920×1080 (`emulatorConfig.h`, справка в `main.cpp`) вместо 1280×720; в `.porting/work/extra_env.sh` (основное приложение `KyTxMetal.app`) добавлен `KYTY_EOP_CLOCK_FREEZE=1`, чтобы игра не «дышала» 1600×904 (задокументированный обход, не корректное решение). `KYTY_VIDEO_OUT_1080P=1` уже стоит в лаунчерах. ## Правила и цена прогонов

- 2026-10-28 пользователь разрешил запуски («продолжай чинить разрешаю запуски»); до этого каждый прогон спрашивался отдельно. **Каждый прогон нагружает Mac, при зависании у пользователя лагает интерфейс; два раза зависшее GPU-ядро перезагружало Mac (2026-10-26 20:15, 2026-10-27 ~19:40).** Выход из процесса не останавливает уже выполняющееся ядро. Ставить вотчдог 8 с (`KYTY_GPU_WATCHDOG_S=8`), просить не закрывать окно (в uk9 пользователь закрыл процесс раньше вотчдога — потерян список операций), один эмулятор за раз.
- `run1.sh` отказывается стартовать, если `ps aux | grep "[k]yty_emulator.* --game"` что-то находит. **Ложное срабатывание:** командная строка любой моей Bash/Monitor-команды, в тексте которой есть `kyty_emulator… --game`, совпадает (дважды сорвало запуск). Запускать прогон чистой командой без этого текста, мониторинг класть в файл (`/tmp/mon_uk.sh`, `bash /tmp/mon_uk.sh <tag>`).
- Убивать только свои экземпляры (`.porting/tools/killmine.sh` по RUN_TAG), `pkill` по имени запрещён. GPU/render-поток не берёт мьютекс менеджера гостевой памяти. Без Vulkan/MoltenVK/SPIRV-Cross/Rosetta. zsh: `log` — встроенная, использовать `/usr/bin/log`.
- Перед запуском скрипта читать свежие follow-up'ы в `.porting/` и `stat` скриптов: соседние сессии правят то же дерево (так я перебил их правку cap 4096 → 256 в uk10 и остановил свой прогон через 13 с).

## Что не сходится / не доказано

- Идёт ли затирание от записей в RT-виды (clear/store по полному размеру вида, больше реальной поверхности — динамическое разрешение 1600×904 против 1920×1080) или от гонки между encoder'ами (виды над теми же страницами — другие MTLBuffer/MTLTexture, Metal не видит зависимость). Опровергнуто uk27: без UMA затирание тоже есть (333 срабатывания); SYNC_ENCODERS даёт 0 (uk21, uk28). Остаётся порядок операций (см. «Дополнение»).
- `KYTY_MTL_SPLIT_OPS/DRAWS` скрывал зависание (uk4, uk10) — тоже согласуется с гонкой по времени.
- Три «места зависания» (877–905, 1586–1955, ~10725) в старых прогонах — смесь артефакта cap 256 и этой проблемы; на cap 4096 видно только ~1585 (и то не всегда).

## Изменения кода (всё не закоммичено)

Этой сессии (2026-10-28):
- `metalIndirect.mm/.h`: ядро `compute_args` считает все три оси в каждом потоке и обнуляет все, если произведение > `cfg[6]` (4Mi по умолчанию, `KYTY_MAX_INDIRECT_TOTAL_GROUPS`); в `dst[7]` пишется номер dispatch'а; `KytyNoteComputeIndirect(hash, addr, cover)` (кольцо 8192) и `KytyDescribeIndirectArguments()` (читает общие буферы без ожидания: снимок compute-indirect и первые 4 записи MDI).
- `metalContext.mm`: вотчдог перед `_exit(3)` печатает `[GpuWatchdog] indirect snapshots: …` (номер, групп Metal, исходные аргументы, ядро, адрес, поверхности над ним).
- `metalRenderer.mm`: `GpuSurfacesCovering()` + запись в кольцо после `converter.Encode`; лог `[IndirectArgs] cs=… args=… covered by: …` (первые 200 пар).
- `tests/metalPipelineTests.mm`: 3 случая (`0x3F800000×3`, `UINT32_MAX×3` → 0 групп; 2048×1024 → выполняется). `tools/test_metal_pipeline.sh` с Metal API и shader validation: compute indirect 10 случаев, 0 ошибок; MDI 17 + 5 + 3, 0 ошибок.

Ранее (uk1–uk9, 10-27/28): per-буферный вотчдог (`KytyWatchCommandBuffer`, `WaitUntilIdle`/SYNC_ENCODERS/вспомогательные буферы), метки `draw_idx` с `inst/fi/bv`, `KYTY_MTL_SYNC_EACH/SPLIT_OPS/SPLIT_DRAWS`, `.porting/work/hang_run.sh`, `stall_sample.sh`. **Исправления к прежним записям:** `DispatchIndirect` не «повторял прошлый pipeline», а молча пропускал indirect-dispatch (чинит Codex); зажим групп теперь в `MetalComputeIndirect` (GPU), не в `metalDraw.mm`; `KYTY_SKIP_EMPTY_DRAWS` теперь не трогает MDI-заглушки; `idx=1`-draw'ы в зависшем буфере — заглушки indirect multi-draw (Codex).
