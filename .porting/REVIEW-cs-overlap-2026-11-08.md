# Обзор KYTY_CS_OVERLAP и стоимость барьеров Metal 4 (2026-11-08)

Автор: Claude (агент-аудитор). Игру не запускал, существующие исходники не менял, новые файлы: `tools/bench/metal4_barrier_cost.mm`, `tools/bench/run_metal4_barrier_cost.sh`, этот отчёт.
Железо: Apple M5 Max, macOS 27.2 (26B123), SDK из Xcode с заголовками Metal 4 (`MTL4CommandQueue`, `MTL4ComputeCommandEncoder`, `MTL4ArgumentTable`, `MTLGPUFamilyMetal4` поддержан).
Все числа получены на машине, где параллельно работал другой агент с эмулятором: разброс между прогонами до +-30% (иногда x2 на GPU). Ниже даны медиана и диапазон по 4 полным прогонам (`bench` занимает ~3 с, нагрузка пренебрежимо мала).

## 0. Короткий итог

1. **Метал 4 не дешевле fence'ов между энкодерами.** `MTLFence`-цепочка Metal 3, `MTLFence` Metal 4 и queue-барьер Metal 4 (`barrierAfterQueueStages:beforeStages:`) стоят одинаково: ~7-10 мкс GPU на энкодер при 1000 мелких запусков (3B 7.7 мс, 4B 7.8 мс, 4Q 8.0 мс). Энкодер Metal 4 сам по себе дороже энкодера Metal 3 (4A «без порядка» 9.9 мс против 3A 3.0 мс). Выигрыш даёт не API, а структура: один энкодер на много запусков + барьер на группу.
2. **Барьер внутри энкодера Metal 4** (`barrierAfterEncoderStages:beforeEncoderStages:`) ~1.6 мкс против ~2.0 мкс у `memoryBarrierWithScope:` Metal 3 в concurrent-энкодере (~20% дешевле, на границе шума). `MTL4VisibilityOptionNone` и `Device` стоят одинаково и обе дают верный результат в тесте зависимой цепочки. Относительно текущей fence-цепочки (3B): барьер после каждого запуска 4.5x быстрее (1.7 против 7.7 мс), барьер раз в 8 запусков 28x (0.27 мс) на мелких, 14x на средних, 2.9x на крупных (1024 групп).
3. **Переход на Metal 4 ради барьеров не нужен**: тот же результат даёт `MTLDispatchTypeConcurrent` + `memoryBarrierWithScope` на Metal 3 (3F: 0.43 мс против 3B 7.7 мс при мелких запусках, 18x).
4. **Неожиданный и самый важный результат** (части 5 и 6 бенчмарка): на этой GPU Metal 3 **никогда не перекрывает подряд идущие serial-энкодеры compute внутри одного command buffer**, даже без fence'ов и без hazard tracking (0 ошибок из 262144 слотов x 100 зависимых запусков x 5 прогонов, контрольный concurrent-энкодер без барьера даёт ~100-150 тыс. ошибок). Порядок ломается только (а) между compute и render энкодерами на непротоколируемых (untracked) ресурсах и (б) между разными command buffer одной очереди на untracked ресурсах. Tracked-ресурсы (умолчание, так создаются все буферы KyTx) Metal упорядочивает сам, в том числе при доступе по сырому GPU-адресу + `useResource` (так привязана гостевая память в KyTx).
   Следствие: **`KYTY_CS_OVERLAP` в нынешнем виде (независимые serial-энкодеры без ожиданий друг друга) не даёт настоящего параллельного исполнения**; его выигрыш равен только убранным fence'ам (~5-6 мкс GPU на энкодер, при ~230 compute/кадр это ~1.2-1.4 мс из ~29 мс кадра). Для реального перекрытия нужен один постоянный concurrent-энкодер и барьеры по группам.
5. По коду overlap-режима: **логика групп и fence'ов (metalOrder.h) верна, незадекларированных обращений к гостевой памяти, ведущих к небезопасному перекрытию, не найдено**; есть два реальных недочёта в объявлении (раздел 3: размер образов `CsAccessBytes`, повторное чтение `CsOverlapEnabled()` в режиме toggle) и список незащищённых fence'ом blit-энкодеров, который к overlap не относится, но отдаёт защиту целиком Metal hazard tracking.
6. Падение `runtimeLinker.cpp:790` **overlap не объясняется**: такой же гостевой краш (адрес `0x88`, потоки Job*, мусорные указатели) записан в хэндоффах с 2026-10-25, включая прогон `mc41` без каких-либо env-переключателей, ~1 из 4-7 запусков. Одно падение в 3 прогонах с ON статистически неотличимо от фона.

## 1. Задача 1: бенчмарк (`tools/bench/metal4_barrier_cost.mm`)

Запуск: `tools/bench/run_metal4_barrier_cost.sh` (собирает и запускает под `nice`). `BENCH_PARTS=15` запускает только части 1 и 5. Использует тот же ядро/размеры, что и `metal_encode_cost.mm`, добавлены колонки wall.

Metal 4 в этом SDK: `MTL4CommandQueue` + `MTL4CommandAllocator` + `MTL4CommandBuffer`, `MTL4ComputeCommandEncoder` (compute + blit в одном энкодере), `MTL4ArgumentTable` (нет `setBytes`, константы лежат в буфере, адрес берётся `setAddress`), `MTLResidencySet` обязателен, время GPU берётся из `MTL4CommitFeedback`. Барьеры: `barrierAfterEncoderStages:beforeEncoderStages:visibilityOptions:` (внутри энкодера), `barrierAfterQueueStages:beforeStages:visibilityOptions:` (потребитель, в начале энкодера, против работы предыдущих энкодеров очереди), `barrierAfterStages:beforeQueueStages:visibilityOptions:` (производитель). Плюс `updateFence:afterEncoderStages:` / `waitForFence:beforeEncoderStages:` и `signalEvent/waitForEvent` на очереди. Кодирование энкодеров, конечно, в Metal 4 ничего автоматически не упорядочивает.

### 1.5 Части 5 и 6: что Metal упорядочивает сам (Metal 3, без fence и барьеров)

Зависимые шаги «читать, крутить цикл, писать» (чётные шаги долгие, нечётные короткие: перекрытие даёт потерянные приращения). 100 шагов по 262144 потоков, 5 прогонов, число неверных слотов:

| вариант | результат |
|---|---|
| КОНТРОЛЬ: один concurrent энкодер, без барьера | 100-180 тыс. неверных |
| один энкодер на шаг, буфер через setBuffer, tracked / untracked | 0 / 0 |
| то же, буфер через сырой GPU-адрес + `useResource(R\|W)`, tracked / untracked | 0 / 0 |
| то же, текстура через дескриптор в буфере + `useResource`, tracked / untracked | 0 / 0 |
| каждый энкодер в своём command buffer, **untracked** | 155-262 тыс. неверных (перекрывается) |
| каждый энкодер в своём command buffer, tracked | 0 |
| compute (долгий) -> render, setBuffer, **untracked**, без fence | ~255-262 тыс. неверных |
| render (долгий) -> compute, setBuffer, **untracked**, без fence | 60-261 тыс. неверных |
| то же на **tracked**: setBuffer и сырой адрес + `useResource`, оба направления | 0 |
| compute -> render, untracked, **с fence-цепочкой KyTx** | 0 |

Значит: (1) подряд идущие serial-compute энкодеры одного command buffer исполняются строго по очереди на этой GPU без всякой синхронизации; (2) перекрытие возможно между энкодерами разных типов и между command buffer'ами, но Metal hazard tracking его гасит для любого tracked-ресурса, включая доступ по сырому адресу, если ресурс передан в `useResource`; (3) значит fence'ы KyTx реально нужны там, где tracking ничего не видит: разные Metal-объекты над одной памятью, сырые указатели через BDA, untracked-ресурсы. Это не гарантия API (документация обещает только то, что описано в заголовках); тест (часть 5) занимает 3 секунды, его стоит гонять после каждого обновления macOS.

## 2. Как устроен overlap-режим (прочитано)

- `metalOrder.h`: глобальное состояние `OrderDetail::State` под мьютексом. `frontier` = fence'ы, которых ждёт следующий энкодер. Для не-compute энкодеров (`OrderBegin` render/blit/compute) ждут весь frontier и закрывают группу. Для dispatch (`OrderBeginCompute`): если `unknown`, или нет открытой группы, или в группе 8 запусков, или есть конфликт диапазонов (запись против чтения/записи, гранулярность 16 КиБ), запуск становится «лидером» (ждёт весь frontier, открывает группу); иначе «членом» (ждёт `group_base` = frontier на момент открытия группы, а не других членов). `OrderEnd*` обновляет frontier: лидер/Full заменяют его одним fence, член добавляет. Кольцо из 64 fence'ов. Я проверил переходы состояний `Full/Leader/Member/None`: инварианты соблюдены (лидер после конфликта ждёт все fence'ы предыдущей группы, любой неупорядоченный по группе энкодер ждёт всех членов, `unknown` всегда отдельная группа с обеих сторон).
- `metalDraw.mm:528-571`: `BeginComputePass` создаёт энкодер, при overlap откладывает ожидание (`m_order_pending`) до `Dispatch/DispatchIndirect` (`BeginDispatchOrder`), когда известен список доступов; пустой список = unknown.
- `metalRenderer.mm` `DispatchCompute`: объявляет (а) аргументы indirect (чтение 12 байт, 9133), (б) каждый буфер из `snap.buffers[b]`: `[addr, addr+size)`, запись, если в шейдере хоть один store/atomic (`resource.written`, `ResourceTracking.cpp:1718`), (9331), (в) GDS как запись псевдодиапазона `0xFFFFFFFFFFF00000` (9394), (г) `BdaPagetable` -> unknown (9399), (д) каждый образ `[addr, addr+CsAccessBytes)`, запись для storage (9899).
- Важно для оценки пользы: по умолчанию гостевые буферы это **буфер на 64-МиБ физический чанк** (`metalBuffer.mm:261-299`), создан `newBufferWithBytesNoCopy` без режима отслеживания = tracked. Metal отслеживает hazards по целому объекту, поэтому два dispatch'а с непересекающимися диапазонами в одном чанке всё равно упорядочены драйвером.

## 3. Задача 2: что dispatch может трогать и объявлено ли это

Вердикт: БЕЗОПАСНО (как есть), ЧАСТИЧНО, НУЖНО ДОБАВИТЬ.

| путь доступа | как покрыт | вердикт |
|---|---|---|
| Сырые гостевые указатели через BDA page table (`global/flat/scalar-address` загрузки, BVH, `IndirectBuffer` = V# выбирается на GPU) | `uses_dma` (`ResourceTracking.cpp:1835, 1869, 1908`) -> `BindingLayout.cpp:154` добавляет `BdaPagetable` -> `ComputeAccessUnknown()`. Unknown-запуск всегда лидер, закрывает группу с обеих сторон | БЕЗОПАСНО. `FlatLocal`/`Scratch` (потоковые) не ходят в гостевую память и не помечаются |
| Цепочка указателей (указатель лежит в объявленном буфере, дальше разыменование) | то же самое: разыменование = raw-адрес = `uses_dma` | БЕЗОПАСНО |
| Атомики на общих счётчиках | буферный atomic => `written` (read+write), конфликтует с любым доступом к страницам; GDS atomic => псевдодиапазон записи; image atomic => storage => запись; raw-адрес => unknown | БЕЗОПАСНО (консервативно: два коммутативных atomic-добавления тоже не перекрываются) |
| UAV/буферы, привязанные не через `snap.buffers` | другого пути нет: все привязки идут через `snap.buffers[b]` (в обоих ветках: `arg_ptrs` и `MTLArgumentEncoder`), debug-буферы 26-29 создаются на dispatch | БЕЗОПАСНО |
| Размер буферного объявления | `size` = размер V# (`sizes[b]`), все load/store в MSL проверяются по `sizes[b]` (`MslEmitter.cpp:829, 850, 2049, 2084`), затем `sizes[b]` ужимается до фактического буфера: доступ не выходит за объявленное | БЕЗОПАСНО. `size==0` => объявлено 4096, а доступов нет |
| Образы по любому из путей (`layered, bclevel, rtmip, uma, lastwriter, rt, csreg, alias, guest`) | объявление ключом по базовому адресу T# `addr`; все пути, дающие один и тот же Metal-объект, ключуются одним адресом; mip-view/ReinterpretFormat/ApplyDstSel это тот же объект. Любые два доступа к одной цепочке mip начинаются с `addr` и пересекаются на первой странице | БЕЗОПАСНО для одного базового адреса |
| Образы над гостевой памятью (`uma`: буфер-бэкед текстура) и перекрытие образа с буфером другого базового адреса | зависит от `CsAccessBytes` (`metalRenderer.mm:8695`): `w*h*d*layers*bpp`, +25%, x2 при mip, минимум 4096; страничное округление 16 КиБ даёт запас | **ЧАСТИЧНО** (см. R1): недооценивает куб (x6 граней не учтены), «тонкие» образы с выровненным pitch (`bufferBytesPerRow*h`), хвост mip-цепочки, 3D с mip; для сжатых форматов `BytesPerPixel` может быть 0 |
| Образы разных базовых адресов, ссылающиеся на один хостовый объект | реестры ключуются по адресу (`LastGpuWriterTexture(addr)`, `GetComputeWrittenImageForAddress(addr)`, `NewestRenderTargetFor(addr,w,h)`), так что один объект достижим только по одному адресу | БЕЗОПАСНО; плюс tracked-текстуры (тест части 5) |

### Ранжированные находки

R1 (средний). `CsAccessBytes` недооценивает гостевой след образов (куб x6, «тонкие» образы с выровненным pitch, хвосты mip, 3D+mip; для буфер-бэкед текстуры известен точный размер `bufferBytesPerRow*height*slices`). Важно только для пересечения образа с другим базовым адресом (UMA-поверхности над общей памятью, буфер поверх образа), для одной базы конфликт виден всегда. Исправление: для `t.buffer != nil` брать `bufferOffset..bufferOffset+bytesPerRow*height*layers`; для `MTLTextureTypeCube/CubeArray` множить на 6; для сжатых форматов брать размер блока; общий запас сделать x2 (дёшево: страничная гранулярность и так грубая).

R2 (средний, только режим `toggle`). `CsOverlapEnabled()` вычисляется заново при каждом объявлении (пять мест: 9133, 9331, 9394, 9399, 9899) плюс в `BeginComputePass:544`; в режиме toggle он читает `TraceWindow::g_flip`, который меняет другой поток. На границе фазы в середине `DispatchCompute` часть доступов объявлена, часть нет, а непустой неполный список считается «независимым». Исправление: один раз в `BeginComputePass` сохранить `m_overlap_active`, и использовать его во всех `ComputeAccess*`; плюс флаг «объявление завершено» перед `Dispatch` (иначе unknown).

R3 (низкий). Энкодеры общего потока без `OrderBegin/OrderEnd` (список в таблице выше). Не новый риск, но overlap делает Metal hazard tracking единственной защитой. Добавить `OrderBegin/OrderEnd` или явно пометить как `s_unordered`.

R4 (низкий). Общая записываемая подставка `NullImageFor(storage)` и `s_scratch`: объявить как запись (псевдодиапазон, как у GDS) или считать unknown.

R5 (информация, влияет на ожидания). Счётчик `overlapped` в логах `[CsOverlap]` считает «объявлено независимым», а не «реально выполнялось одновременно». По части 5 serial-энкодеры одного command buffer не перекрываются в любом случае, а чанк-буферы tracked, так что Metal сам их упорядочит. Реальная польза режима = убранные fence'ы.

R6 (информация). Кольцо из 64 fence'ов и список `frontier` безопасны при условии, что порядок кодирования = порядку фиксации command buffer'ов одной очереди и что кодирует один поток под `m_mutex`; `Kind::None` (энкодер без dispatch) добавляет fence в frontier без ожидания, список сбрасывается следующим лидером/Full, рост ограничен. Это стоит записать комментарием.

Других путей к необъявленным доступам не нашёл: все ресурсы идут через `snap.buffers`, `snap.images`, GDS, BDA (unknown) и динамические кольца (создаются под dispatch).

### Может ли дизайн объяснить падение `runtimeLinker.cpp:790` (`Unhandled host exception`, адрес `0x88`)

Нет, по трём причинам.
1. Оно старше overlap. Хэндоффы 2026-10-25 (`...evening.md`, пункт 4), 2026-11-01, 2026-11-04 описывают те же «случайные падения гостя» в Job-потоках с мусорными указателями (~1 из 4-5 длинных прогонов). `CODEX-clothes-metal-2026-11-07.md:222` и `HANDOFF-claude-2026-11-08-anomalies-nan-neon.md:143, 147` фиксируют `runtimeLinker.cpp:790`, адрес `0x88` в прогоне `mc41` **без env-переключателей** (≈1 из 7 запусков). Overlap по умолчанию выключен и появился позже.
2. Для порчи гостевой CPU-памяти GPU должна записать по неверному адресу. Написать по произвольному гостевому адресу может только kernel с BDA (unknown): он всегда лидер и ждёт весь frontier, поэтому видит завершённые данные предшественников. Остальные kernel'ы ограничены `sizes[b]` внутри объявленных буферов/образов. Перекрытие serial-энкодеров в одном command buffer на этой GPU не происходит (часть 5), tracked чанк-буферы упорядочивает драйвер, так что даже ошибка в объявлении не превращается в реальную гонку между compute-запусками.
3. Единственный путь, где overlap мог бы стать причиной: в режиме `toggle` на границе фазы неполное объявление (R2) + реальное перекрытие членов через разные Metal-объекты над одной памятью. Для этого нужен конфликт именно через разные базовые адреса и недооценку размера (R1), то есть событие редкое и порча была бы данными GPU, а не CPU-структурами.
Логичнее продолжать искать в CPU-стороне (FEX/TSO векторные операции, HLE); для различения нужен счёт: при фоновой частоте ~14% разница 1 из 3 против 1 из 7 неразличима, надо хотя бы 15-20 запусков на ветку. Полезно запускать с `KYTY_FEX_FAULT_RIP=1` (печатает гостевой RIP/блок), чтобы сравнить место падения с `mc41`.

## 4. Рекомендации

1. **Не переходить на Metal 4 ради барьеров.** Эффект даёт concurrent-энкодер + барьер, доступный и в Metal 3. Если backend когда-нибудь переедет на Metal 4 по другим причинам: один `MTL4ComputeCommandEncoder` на много запусков (compute+blit в одном энкодере), `barrierAfterEncoderStages` с `Device`, не энкодер-на-запуск.
2. **Для настоящего параллелизма**: держать открытым один `MTLDispatchTypeConcurrent` compute-энкодер между вызовами `DispatchCompute`; границы групп, которые уже считает `OrderBeginCompute` (конфликт/unknown/8 запусков), превратить в `memoryBarrierWithScope:MTLBarrierScopeBuffers|MTLBarrierScopeTextures` вместо fence'ов; любой другой энкодер/commit закрывает concurrent-энкодер и ставит Full fence. Внутри concurrent-энкодера Metal hazard tracking НЕ действует (контроль части 2/5: ошибки), поэтому объявления доступов становятся единственной защитой и R1/R2 надо исправить до этого. Оценка по бенчмарку: 3F против 3B на мелких запусках 0.4-0.9 мс против 7.7-8.4 мс на 1000 (18x на мелких, ~14x на средних), на крупных 3.6 против 10.1 мс. Для кадра с ~230 compute-dispatch это 1.2-1.4 мс GPU из ~29 мс (4-5%) только на compute; прибавка реальной параллельности мелких ядер неизвестна и зависит от того, как часто группы большие.
3. **Дешёвая проверка до любых правок**: сколько стоят fence'ы в реальном кадре? `KYTY_ENCODER_FENCES=0` (существующий переключатель) даёт верхнюю границу экономии ценой возможных артефактов (части 5-6: между compute и render без tracking ломается; в KyTx буферы tracked, но алиасы между объектами не защищены). Мерить на сцене, ограниченной GPU (матч), по `KYTY_GPU_BUSY`/`KYTY_MTL_GPU_TIME`.
4. **Возможная прямая экономия без overlap-анализа**: не ставить wait/update между двумя подряд идущими compute-энкодерами одного command buffer (на этой GPU они и так исполняются по очереди, часть 5), оставив fence'ы на смене типа энкодера и на границе command buffer. Это та же экономия ~5 мкс на энкодер, что и у overlap-режима, но без анализа диапазонов и без риска ошибки объявления. Поведение не гарантировано API: оформить переключателем и гонять часть 5 бенчмарка после обновлений macOS.
5. Исправить R1 и R2, добавить `OrderBegin/OrderEnd` в энкодеры из R3, пересчитывать `[CsOverlap]` как «серийная группа», а не «перекрылись» (R5).
6. Если нужна настоящая независимость диапазонов на уровне драйвера: чанк-буферы создавать с `MTLResourceHazardTrackingModeUntracked` (иначе Metal сериализует по объекту целиком). Это сразу делает fence'ы и барьеры единственной защитой, включая алиасы текстур над гостевой памятью, и меняет всю модель безопасности: только отдельным, хорошо проверяемым шагом.

## 5. Ограничения

- Всё измерено на одной машине и одной версии ОС; поведение «serial-энкодеры не перекрываются» не гарантия API. Данные шумные (другой процесс использует ту же GPU), числа даны с диапазонами; все выводы выше устойчивы к разбросу, кроме «Metal 4 барьер на ~20% дешевле» (в шуме).
- Бенчмарк использует запросы GPU-времени из `GPUStartTime/GPUEndTime` (Metal 3) и `MTL4CommitFeedback` (Metal 4); wall-время (commit до завершения) добавляет ~0.15 мс.
- Количество compute-dispatch в кадре (~230) и ~29 мс GPU взяты из `WORKLOG-anomalies-2026-11-08.md`, я их не измерял.
- Эмулятор я не запускал; код только читал (метки строк `metalRenderer.mm` соответствуют рабочей копии на 2026-11-08, она изменяется другими агентами).
